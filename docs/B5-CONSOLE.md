# B5 控制台：决策记录

> 本文是 B5 的设计与决策记录，不是用户手册。§6.5 把控制台本身封存在 P6，只要求 P0 埋三处钩子；
> 本文回答的是「P6 的**后端**在 P1–P5 全部闭合后应该是什么形状」，以及每个形状背后的取舍。
>
> 证据（命令与结果）在 `docs/EVIDENCE.md`；任务状态在 `docs/TODO.md`。

## 1. 范围：为什么这一轮只有后端 API

P6 的原文范围含「控制台」三字，字面上可以是前端界面。这一轮不做界面，理由是**依赖面**，不是工作量：

- 仓库到目前为止**没有**任何前端依赖、构建链或静态资源目录（`go.mod` 的依赖列表短到是刻意维护的）。
  引入一个界面意味着引入 npm/打包/模板链，而这些东西对本仓库的核心立论——热路径可读、慢路径可算——零贡献。
- 界面的**数据形状**才是需要现在定死的东西：哪张表、哪些字段、谁能看。界面是对这些端点的消费者，
  可以后加；端点形状定错了，界面跟着错，且返工面更大。
- 三个钩子里真正有工程内容的是查询与写操作的**边界**（谁能读、写什么、写了之后账怎么对上），
  这些和后端同构。

因此 B5 的产物是 `/v1/*` 的一组 JSON 端点。前端界面若要做，是一个新的、独立的、**不阻塞任何 `[no-cred]` 任务**的条目。

## 2. 身份：运营凭据与租户凭据分离

§6.4.1 只约束了 gateway 与客户端之间的身份边界，**没有**提控制面。这是个真空，必须显式填。

**决策**：控制台用独立的运营 token（`GATEWAY_CONSOLE_TOKEN`），**不复用**租户 token，也不加运营标记。

> **2026-09-14（B5.1）**：从一枚 token 改为**两级**。`GATEWAY_CONSOLE_TOKEN` 可读写，
> 可选的 `GATEWAY_CONSOLE_READONLY_TOKEN` **只读**。授权按**方法**判定
> （本包所有写路径都是 `POST`，所有读都是 `GET`），因此不存在「新加的 handler 忘了登记」
> 这种漏网方式——新端点默认只读，一旦它是 `POST` 就已经被保护。
> 两个 token 配成同一个字符串时**拒绝启动**：把它当读写会把写权交给每个「只读」持有者，
> 当只读又会让所有写路径莫名 403，两种读法都会误导人。
> 只配只读 token **不启用**控制台（更可能是配错，而不是有意运行一个永久只读的控制面）。

被否决的两个选项与理由：

| 选项 | 否决理由 |
|---|---|
| 复用租户 token + 运营标记 | 租户 token 是**客户端凭据**，它的整个生命周期都在客户端手里。一旦某个租户 token 被授予运营能力，这个能力就进入了租户可触及的面，而钱包、单价、全租户的账号健康都在这个面后面。§6.4.1 的立论是「请求体中的同名字段不可信」——同样的推理要求运营身份不能来自同一个通道。 |
| 不做鉴权，只绑 loopback | 控制面一旦可达就是**全量**数据暴露：所有租户的钱包与流水、单价表、所有账号的健康与冷却、全量请求明细。这远超单个租户的可视范围。loopback 是可以叠加的纵深（默认地址就是 `127.0.0.1:9092`），不能是唯一防线。 |

两个后果是**选择**而非疏漏，写在这里以免被当成 bug：

1. **没有运营者目录。** `billing_resolutions.operator` 与 `account_actions.operator`
   记的是调用方通过 `X-Operator` 头**自称**的名字，用于人工可读的审计，不是经过认证的身份。
   真正的多运营者权限体系是一套独立的访问控制系统，**B5.1 的两级也不是它**——
   能力分级是爆炸半径控制，不是认证。所以 `X-Operator` **不参与**任何授权判断——
   `TestOperatorHeaderIsNotAuthorization` 断言了这一点。
2. **token 未配置时控制台整体关闭**，不是「无鉴权开放」。缺一个环境变量必须是
   「没有控制台」与「无鉴权控制台」之间的差别，不能反过来。

监听地址与 metrics 分开（metrics 在 `:9091`，无鉴权；控制台默认 `127.0.0.1:9092`）。
把运营 API 挂到 metrics 端口上会让一个无鉴权端口增加一个特权邻居，反过来也一样。

## 3. 三处钩子的落点（§6.5）

| §6.5 钩子 | 后端来源 | 端点 |
|---|---|---|
| 账号健康看板 | A9 写入的 `accounts.last_error_class/at`、`consecutive_failures`、`cooldown_until`、`excluded_models` | `GET /v1/accounts` |
| 用量报表 / 对账 | B4.2/B4.5 的 `usage_ledger`、`wallet_transactions`、`tenant_wallets` | `GET /v1/billing/reconcile`、`GET /v1/billing/wallets/{tenant}` |
| 实时请求日志 | A12 的 ClickHouse 明细 | `GET /v1/requests` |

三者共用一件事：**都是读**，且都读的是已经存在的权威存储。控制台不自己算账、不自己判健康，
只是把已记录的状态读出来。这不是实现上的巧合，而是 §6.4 的直接推论——control 的单写者路径
只随账号数增长，控制台的查询如果开始做聚合计算就会破坏这一点。

`accounts` 的响应**刻意**不含 `credential_id`、`base_url`、`proxy`、`model_mapping`：
控制台面向的读者多于一人，而这些字段是 §6.4.1 要求不出现在任何客户端可达面的东西。

## 4. 三个写操作，以及为什么是这三个

只读的控制台不解决任何遗留问题。三个写端点各自关闭一处此前被显式记录为「没有入口」的缺口：

### 4.1 held 行裁定（B4.3 遗留）

B4.3 把「请求成功但 usage 丢失」的行放进 `held`，并在 B4.3、B4.5、E1 三处记录了
「人工处理入口未做」。E1 的告警文案甚至直接写着「目前也还没有人工处理的入口（见 TODO 未决项）」。

裁定只有两个合法值，且都**必须显式给出**：

- `bill` —— 按 `occurred_at` 当时生效的单价计费，与 B4.2 作业的口径完全一致。
- `write_off` —— 判定为零，行进入 `not_billable`。这是一个**决定**，不是「没决定」；
  B4.3 创建 `not_billable` 正是为了让核销不能和「没人看过」混淆。

三个由此推出的性质：

1. **`bill` 可能返回 `unpriced`。** D3 禁止单价追溯，所以一条在无单价期间发生的行
   **永远**不可能被定价。诚实的结局是终态 `unpriced`，不是拒绝请求（会把运营卡住），
   也不是静默按零计费（B4.0 明令禁止的隐式默认）。响应里的 `outcome` 字段说明到底发生了什么。
2. **裁定与账目变更在同一事务。** `billing_resolutions` 的写入、`usage_ledger` 的状态更新、
   钱包扣款三者一起提交或一起回滚。
3. **人工计费行携带合成 run id，因此 B4.5 照样对得上。** B4.5 按 `billing_run_id` 分组，
   把该组的 ledger 金额与携带同一 id 的钱包扣款比。人工计费沿用同一约定，
   对账**不需要知道**中间有人介入。`TestConsoleResolveHeldBillsARowAndReconciles` 断言了这条。

零金额的计费**不写**钱包流水，与 B4.2 作业一致：一条零金额流水在对账里只是噪音。

### 4.2 充值（B4.1 遗留）

B4.1 把充值入口留给 B5。两点是刻意的：

- **钱包不存在时创建。** 充值正是钱包诞生的时刻；要求先「建钱包」再充值，会让一次失败的
  建钱包把充值变成静默无效。
- **重复的 id 不是错误。** `id` 是调用方给的幂等键，直接做 `wallet_transactions` 主键；
  重放返回原始流水。超时后重试是安全的，不可能重复入账。

这不是支付集成：B4-BILLING-MODEL §2 把支付渠道划在范围外，这个端点记录的是**通过其他途径到账**的钱。

### 4.3 单价录入（B4.1 遗留）

B4.1 交付了 `model_prices` 表和不可变触发器，但**没有任何写入方**——整条计费管线因此无法配置。
这个端点补上它，并且：

- **不能改价。** 仓储没有更新入口，数据库触发器连 psql 都改不动历史行。
- **`effective_from` 必填且必须在未来。** D3 要求改价只向未来生效；控制台让运营**显式**给出生效时刻，
  而不是继承「现在」。
- **它不是计费动作。** 不重算任何已结算行；晚到的单价只适用于生效之后的用量，
  生效之前的用量成为 `unpriced`（B4.3 判定的终态），只能靠显式钱包调整修正，不能靠倒填单价。

## 5. 明细查询：只读、绑定参数、绝不求和

`GET /v1/requests` 是唯一读 ClickHouse 的端点，也是唯一可能有注入面的地方（租户、窗口都是用户输入）。

- 租户、provider、窗口全部走 ClickHouse 的 `{name:Type}` 绑定参数（`param_*`）。
  只有 `limit` 渲染进语句，且先被钳制到 `[1, 500]`。
  `TestConsoleRequestLogBindsTheTenantFilter` 用一个带引号和 `DROP TABLE` 的租户名断言：
  返回零行、不报错、表还在。
- **明细被禁用时返回 503 并说明原因**，不是空列表。「没有配置明细」和「没有匹配的请求」
  必须长得不一样。
- **端点只返回行，不做任何求和。** A12 与总览 §6.4 都写明了：账的权威只有 `usage_ledger`，
  明细是可丢的运维视图。控制台若对明细做求和展示，就是在制造第二本账。

`Record` 的字段在 `internal/detail` 里是**封闭**的（没有自由 map、没有 header 袋、没有请求体字段），
读取侧的 SELECT 列表由该结构体的 json tag **推导**而非手写，所以不存在
「写入有、读取无」或两侧字段名不一致的可能。`internal/detail/query.go` 里同一条注释说明了这个推导的理由。

## 7. 账号的人工操作（B5.1）

三个动作，都是 `POST`，都需要**读写** token：

| 端点 | 作用 | 说明 |
|---|---|---|
| `POST /v1/accounts/{id}/status` | `{"status":"active\|disabled","reason":"..."}` | `reason` **必填** |
| `POST /v1/accounts/{id}/cooldown/clear` | 清 `cooldown_until` **与** `consecutive_failures` | `reason` 可选 |
| `POST /v1/accounts/{id}/excluded-models/clear` | 清空 `excluded_models` | `reason` 可选 |

**三条贯穿全部动作的规则**，每条都对应一个具体的出错方式：

1. **都不直接触达 gateway。** §3 的 P0 决策是 control 与 gateway 只共享快照与 Release 流，
   无同步 RPC。所以动作只写 PG，由 A1 快照循环在下一个 tick（`snapshotRefreshInterval`，1 分钟）
   带过去。响应里的 `effective_within_seconds` **明说**这件事——
   否则「我禁用了它，它还服务了三个请求」会被当成 bug 报上来，而那其实是文档化的设计。
2. **都递增 `fence_epoch`。** 不递增的话，一个正在途中的凭据刷新或 wrapper job 会带着旧 epoch
   把结果**盖在运营的决定之上**。递增让那个陈旧写者的 CAS 失败——这正是 `ErrFenceLost` 的用途。
3. **都写 `account_actions` 审计行，且与账号更新同事务。** 与 `billing_resolutions`
   对金钱的论证同构：改了调度行为却没留下「谁、为什么」的记录，事后无法解释。
   表是**追加型**的，`UPDATE`/`DELETE` 由数据库触发器拒绝。

**两处刻意的行为**：

- **无变化即不算数**：重复禁用一个已禁用的账号**不递增 epoch、不写审计行**。
  否则一次无意义的重试就会白白作废一个正在进行的刷新。响应用 `applied:false` + `detail` 说明。
- **清冷却清不掉 gateway 的那一半**：gateway 有自己的**进程内**冷却表（§6.3.1 的桥接），
  control 够不着它（无 RPC、快照也不带）。响应里 `gateway_local_cooldown_note` 直说这一点。
  含糊过去会让人去追一个其实是设计的「bug」。

## 8. 分页（B5.1）

`GET /v1/accounts` 与 `GET /v1/billing/held` 接受 `cursor`，返回 `next_cursor` 与 `has_more`。

**用 keyset 而非 OFFSET**，理由不是性能：这些表在运营翻页的同时**还在被追加**，
OFFSET 在移动的集合上会**静默跳过和重复**行。对 held 积压来说，「跳过」意味着
一条待人工裁定的账目被整个迈过去——而按 `occurred_at` 升序排，被跳过的恰恰是等得最久的那条。

游标是不透明的 base64，但**它不保护任何秘密**（内容只是调用方刚读到的位置）。
不透明换来的是日后改排序键而不破坏已存游标的自由，不是机密性。

**多出一行的探测**：查询要 `limit+1` 行，多出的那行只用来证明「还有下一页」，不返回给调用方。
不能用「返回了满页」来推断还有更多——积压恰好是页长整数倍时，会发出一个指向**空页**的游标，
而「最后一页是空的」与「托盘清空了」对翻页的人来说长得一样。
